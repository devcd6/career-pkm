# Career knowledge base: how to read it

This project holds one person's resume history in four layers. This page describes what each layer is and how to interpret it.

## Layers at a glance

```
_raw/        original resume files, untouched
  ↓ copied, organized, tagged
resumes/     organized copies with frontmatter
  ↓ claims extracted, reconciled
kb/          structured claims, each citing its source files
  ↓ summarized
INDEX.md     generated catalog of the above
```

A claim in `kb/` lists source files in `resumes/`. Each of those names its original in `_raw/` (`source_original`). Reading runs in either direction along that chain.

## `_raw/`

- The original files, never edited. Names are arbitrary (`1.md`, `TA4.md`, `MASTER RESUME (AUGUST 2026).md`).
- This is the ground truth for exact wording.
- Stray characters and HTML entities such as `&amp;` are in the originals, not introduced later.

## `resumes/`

- Each subfolder is a group (`master-versions`, `project-coordinator`, `tailored-*`).
- `_archive/` holds files set aside because their content is incomplete or their bullets are merged. Each carries an `archive_reason`.
- File names follow `YYYY-MM_<family>_<group>_v<N>.md`. `vN` is a number within a group, not a ranking.
- Every file starts with frontmatter:

| key | meaning |
|---|---|
| `id` | file name without extension |
| `role_target`, `company_target` | what the resume was aimed at |
| `date`, `date_confidence` | taken from resume content; a lower bound, not an exact date |
| `version_group`, `version_no` | group and number within it |
| `status` | `active` or `archived` only |
| `source_original` | the matching file in `_raw/` |
| `keywords` | the angle or distinguishing content of that resume |
| `archive_reason` | present on archived files only |

- All active resumes carry equal weight. None is "latest" or "superseded".

## `kb/`

### `roles/*.md`
One file per employer role: NCMW, UC Santa Barbara, Sanctuary Centers, ASEI, Casa Serena. Each has role frontmatter (`employer`, `title`, `start`, `end`, `sources`, `status`) followed by achievement blocks headed `### A-...`:

| field | meaning |
|---|---|
| `canonical` | the drafted wording of the claim |
| `tier` | strength of evidence (below) |
| `metrics` | numbers and quantities the claim contains |
| `sources` | the resume files that state it |
| `variants` | every original wording, tagged by source |
| `notes` | differences, caveats, links to conflict ids |

**Tiers**
- `verified`: confirmed by the user.
- `consistent`: two or more versions agree.
- `single-source`: one version only.
- `conflicting`: versions disagree on a fact; the value is not settled.

**Notation inside `canonical`**
- `[A | B | C]` marks interchangeable verb or ownership wordings, for example `[Led | Directed | Managed] …`. The first is the preferred draft. Differences like these are not treated as conflicts.
- `15+ [20-25]` is a canonical value followed by conflicting scope values in brackets.
- Role titles may appear as `Title 1 | Title 2`, listing the variants found.

### `skills.md`, `education.md`, `summaries.md`
Skills, education and certifications, and summary statements, each with the resumes they came from. `skills.md` explains its own line format at the top.

### `_conflicts.md`
One `## C-...` block per disagreement, with `field`, `values` (each with its source files), `status` (`open` or `resolved`) and `resolution`. These cover numbers, dates, scope and employer or education details. Verb and ownership differences are not logged here.

### `_user_decisions.md`
The user's own rulings in their own words, with dates. A resolved conflict or a changed value traces back to an entry here.

## `INDEX.md`

- Generated by `scripts/build_index.py`; not hand-edited.
- The resume table lists raw file name, organized file, target role, date, keywords, and status. Active files come first and archived files follow.
- The roles table lists each role with its achievement count and open-conflict count.
- The status section gives totals for versions, roles, achievements, open conflicts and lint problems.

## Reading rules

- A claim is only as strong as its tier. Treat `conflicting` and `single-source` as unsettled.
- Every claim names its sources. The path is `sources` → `resumes/` → `source_original` → `_raw/`.
- The NCMW title is always "Project Coordinator". "Junior …" and division names are title variants only.
- Dates in `TA4`, `TA6`, `TA7` and `TA8` are the user's authoritative dates.
- The knowledge base records what the resumes say. It is not independent verification.

## Notion sources (added 2026-10-08)

- `_raw/notion/` holds read-only snapshots of pages and databases from the Notion Job Hunt Hub: the Master Career Profile and Master Detailed Resume pages, Writing Samples 1 and 2, and the Job History, Responsibilities, Achievements, Skills and STAR Story Bank databases. Each file's header gives the Notion URL and fetch date.
- Not imported, by the user's instruction: the Documents & Application Material and Notes databases, and the application tracker.
- In `kb/roles/*`, Notion rows appear as `(notion Responsibilities #N)` or `(notion Achievements #N)` lines under `variants:` of the claim they match, and the Notion file is added to that claim's `sources`. Rows with no match are separate `single-source` blocks. Notion's Employment type field is not used (no full-time/part-time on any role). Repo dates win.
- `writing/samples/`: 10 Notion cover letters (verbatim body, with frontmatter); `resumes/` gained 10 Notion tailored resumes (group names `tailored-<role>`; source_original points to `_raw/notion/documents/`).
- `kb/stories.md`: the 15 STAR stories. `kb/skills.md` ends with a Notion Skills section.
- Source paths for these claims start with `_raw/notion/`, not `resumes/`.

## Other folders and files

- `scripts/`: index builder, plan applier, inventory tool.
- `_work/`: working files and plans; not part of the reading path.
- `PROGRESS.md`: checklist of project phases.
- `CLAUDE.md`: project rules.
