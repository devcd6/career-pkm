# apply

Orchestrates one application. Read `CLAUDE.md` (Application mode), `applications/preferences.md`, `writing/style-guide.md` and load all of `kb/_views/claims.md` first. Open a role file in `kb/roles/` only to see variants for one claim ID.

Slug: `applications/<YYYY-MM-DD>_<org>_<role>/` (lowercase, hyphens). Before starting, look in `applications/` and `INDEX.md` for an existing version for the same employer and tell the owner. Every step saves its file and also prints to chat. Stop between steps when the owner wants to review, and ask rather than assume.

1. **/research** (`research.md`). Use the `company-research` skill: six parts (mission and values, programs, leadership and team, challenges and opportunities, funding, culture), each with sourced findings and KB-grounded interview notes, plus a source ledger, red flags and ranked questions to ask. Web queries contain only the employer and role named in the JD, never resume or KB text. Tag every finding with its source or `[JD]`, `[inferred]`, `[not found]`. Run `python scripts/check_research.py applications/<slug>`.
2. **/analyze-jd** (`keywords.md`, `match.md`). Use the `job-description-analyzer` skill with the exact-phrase rules in preferences. `match.md` has the match score, real gaps, open questions. Save the phrases as `keywords.txt` with one `Category | phrase` per line (categories: Title Keyword, Hard Skill, Action Keyword, Business Context, Domain Keyword, Hard Filter, Forced; Forced = short phrase the JD requires verbatim). Use `resume-tailor/scripts/exact_phrase_matcher.py` for phrase counts. `match.md` needs a `## Hard filters` section (the checker requires it) and per-category coverage lines; run `python scripts/rank_claims.py applications/<slug> --out rank.md` for an advisory claim ranking, near-duplicate clusters and phrases no claim contains. Flag "forced keywords" (hard filters the JD requires verbatim).
3. **/tailor** (`plan.md`, then `resume.md`, `claims-used.md`). First run `python scripts/rank_claims.py applications/<slug> --out rank.md`, then write `plan.md`: claims in and claims cut per role (with claim IDs and tiers), bracket and verb picks, near-duplicate choices, real gaps and where each will be framed (cover letter, never the resume), and anything for `proposals.md`. **Stop and wait for the owner's approval of `plan.md` before writing `spec.json` or running `build_application.py`.** Use `resume-tailor`, `resume-bullet-writer`, `resume-section-builder` and `resume-ats-optimizer`. Every bullet maps to a claim ID; `claims-used.md` lists bullet, claim ID, tier and verb chosen from the claim's brackets. Titles, dates and employer names come from the role header in the claims view. Re-screen each bullet as listed in preferences. Print the resume in a markdown code block.
4. **/cover-letter** (`cover-letter.md`). Use `cover-letter-generator` with `writing/style-guide.md` and the two closest samples in `writing/samples/`. Frame gaps honestly here. Numbers only from claim metrics.
5. **/check**. Run `python scripts/check_application.py applications/<slug>` and `node scripts/detect_ai_writing.js applications/<slug>/cover-letter.md` and the vendored `avoid-ai-writing` skill in detect mode on cover-letter.md (never rewrite or edit mode on resume.md), then run `python scripts/check_scope.py`: the diff against main may show only `applications/<slug>/` plus approved root additions. Report failures; do not weaken the checks. Finally write the session handoff to `applications/<slug>/handoff.md` (the `handoff` skill, application-branch rule), run `python scripts/check_handoff.py`, and commit it with the application. The next web session reads it through the `SessionStart` hook.

Optional after step 5, only when the owner asks: `/interview-prep <slug>` (skill `interview-prep`: prep, gaps, debrief).

Rules that never bend: no invented, inflated, rounded or merged facts; new facts go to `proposals.md` first, and reach root (`kb/`, `writing/samples/`) only after the owner's in-session approval, additive only, in a separate `kb: add <what> (approved)` commit with a `kb/_user_decisions.md` entry quoting the approval (CLAUDE.md "Application mode"); never offer to edit Notion; the owner marks anything verified.

## Working notes from earlier applications
- **Build, don't retype.** For step 3, write `applications/<slug>/spec.json` (claim numbers, bracket picks, verbs, summary, skills lines) and run `python scripts/build_application.py applications/<slug>`. It copies canonical wording verbatim and writes `resume.md` and `claims-used.md` with full claim IDs, which the checker requires. Pick the more conservative bracket option ("primary" over "sole") and list the choice in `proposals.md`.
- **Numbers.** Copy the literal form from the metrics ("18+", "6,000+", "20 to 30"). If a bullet's number is missing from its claim's `metrics` (the KB has verified claims with empty `metrics`), list a second claim whose metrics carry it, or pick another claim. A count written as a word in the second claim's metrics ("four") covers its digit in the bullet ("4"), two through twelve. Do not edit the checker further or add `allowed_numbers.txt` to get past it. Record the claim in `proposals.md` so the owner can fill its `metrics`.
- **Cover letters.** Before finalizing, search earlier `applications/*/cover-letter.md` for sentences you reused. The owner's refrains (see `writing/style-guide.md`) may repeat; any other sentence should not.
- **Research.** Names found in third-party directories are unverified; keep them out of the letter and say so in `research.md`. Program names that search cannot confirm are JD wording only.
- **Title and filters.** The role title may appear only in the posting URL; note that in `keywords.md`. Put degree-field and eligibility questions in `match.md` for the owner.
- **Paths.** The shell's working directory drifts between calls. Use absolute paths and re-run the checks from the repo root.
- **Application questions.** When the employer's form has free-text questions, save the answers to `applications/<slug>/application-answers.md`; the AAMC folder is the model. Build them in this order: `research.md` (one verifiable employer detail, the mission wording), `keywords.md` and `match.md` (the JD's own terms and the real gaps), then a short positioning map with the `competitive-cartographer` skill (who else applies, the owner's open space, the gap turned into position) and a values table (employer mission against her through-line, each row tied to evidence). Keep each answer to about 120 to 150 words: lead with the answer, one KB-backed example with its number, name a gap once, then pivot. Use past tense for ended roles (check the role dates in the claims view). Reflections drawn from her cover letters are lessons, not KB claims; list them under open items so she confirms them. Add interview follow-ups and any story the KB cannot supply. Delivery and voice notes are in `applications/profile-insights.md`: it is a self-report aid, never a fact source, and its labels never appear in anything an employer reads. Run the detector on the file (it flags 5 or more bold phrases).
- **Step 5 cost.** The vendored avoid-ai-writing detect pass needs its `references/patterns.md` read in full (about 745 lines). Run the script checks first and the skill pass once, on the final letter.
